## What an element is

An element does one job, and has no smaller part you'd use on its own. A button is an element: its label and icon only
make sense inside it. A card isn't: it holds text, avatars and buttons that live on their own too. Elements are the
second layer of the system, right above the tokens; [Composition](?path=/docs/handbook-composition--docs) explains how
the layers build on each other.

Every element:

- **Does one thing.** It triggers an action, takes a value, shows a piece of media or tells a state.
- **Knows nothing about the product.** A badge shows a label in a tone. It doesn't know what a run or an agent is.
- **Takes no outside space.** No margins: whoever places it sets the gap. Fields fill the width they're given; the rest
  are as wide as their content.
- **Holds only its own state.** A checkbox knows whether it's checked. It never opens, loads or moves something else.
- **Is accessible on its own.** Its role, name, keyboard behavior and focus ring are built in, so every component made
  from it gets them for free.

## Is it an element?

Ask these in order. The first question that sends the piece somewhere else decides where it goes.

1. **Can it be split into smaller pieces that are useful on their own?** Then it's a component made of those pieces. A
   search field is a text field and an icon button.
2. **Does it arrange other things?** Groups, lists, stacks, and anything with room for other elements inside it, are
   components.
3. **Does it open, close or control something else?** A tab and its panel, a trigger and its menu: components.
4. **Does it know about agents, runs or approvals?** Then it lives in AI, however small it is (a run's status). Charts
   and tables live in Data.
5. **Would it look and work the same in any product?** If it passed the questions above, and the answer is yes, it's
   an element.

> **Not sure?** Build it as a component. A piece that turns out to have one job moves down to Elements easily; an
> element that grew a layout is harder to take apart, because everything that uses it depends on that layout.

## Building one

- **Variants and sizes come from a short, fixed list,** like `primary`, `secondary` and `ghost`, or `m` and `l`. A new
  variant is a design decision, not a prop someone adds for one screen.
- **It's an HTML element underneath.** It takes that element's props (`disabled`, `aria-*`, `onClick`…), its `ref` and a
  `className`, so it fits wherever the element it replaces would.
- **Its words are props,** with English defaults, so an app can translate them.
- **It ships with its stories,** a Playground first and one story per variant and state, and its docs page is its
  README.
